## 1. [높음] 조사자 보고서 엑셀 → 간편 가져오기

**배경**: 현행 일괄입력은 계산식이 잔뜩 든 복잡한 전치 엑셀을 요구한다. 조사자 앱이 만든 **깔끔한 보고서용 엑셀**을 그대로 받아 분류군 테이블에 넣는 경로가 필요하다.

- 조사자 보고서 엑셀 구조: `조사개황` / `출현종`(지점명 포함 1행1종) / `건강성평가`(1조사 1행)
  → 상세는 `..\..\SDSM_Surveyor\docs\03_FEATURE_EXPORT.md` §2
- 기존 `Bulk*ControlViewModel` 은 **그대로 두고**(레거시 병행), 별도 메뉴로 추가한다.
- 가져올 때 **지수·등급은 엑셀 값을 신뢰하지 말고 재계산**한다(현행 정책과 동일).
- 신규 종(조사자가 현장에서 추가한 종)은 종 마스터에 **검수 후 병합**할 수 있게 표시한다.

### 2-2. 지점 사진 (신규)

`SurveySite` 에 다음을 추가한다.

```csharp
/// <summary>지점 사진. 사진 폴더 기준 상대경로(예: "생태현황/진위천1/2026_상류.jpg").
/// ⚠ 이미지 바이트를 DB·JSON에 넣지 않는다. 현장 사진은 장당 2~5MB라 DB가 급격히 커진다.</summary>
public List<SitePhoto> Photos { get; set; } = new();

public class SitePhoto
{
    public string RelPath { get; set; } = string.Empty;  // 사진 루트 기준 상대경로
    public string? Caption { get; set; }                 // 예: 상류 전경
    public int? Year { get; set; }                       // 촬영 연도(연도별 변화 비교용)
}
```

**저장 규칙**
- 사진 루트: 관리자 앱 설정에 `SitePhotoRoot` 경로를 둔다(기본 `<앱폴더>\SitePhotos`).
- DB·`sites.json` 에는 **상대경로만** 저장한다. 파일은 절대 DB BLOB에 넣지 않는다.
- 화면에서 [사진 추가] 시 원본을 `SitePhotoRoot\{Project}\{SiteName}\` 로 **복사**하고 상대경로를 기록한다.
- 파일이 없으면 목록에 `(파일 없음)` 으로 표시만 하고 **오류를 내지 않는다.**

**조사자 앱 전달**
- `sites.json` 에는 경로만 들어가므로 조사자 앱에서는 기본적으로 사진이 보이지 않는다.
- 사진까지 전달하려면 **[지점자료 내보내기(사진 포함)]** 를 별도 버튼으로 만들어
  `sites.json` + 사진을 하나의 zip으로 묶는다. 이때 사진은 **긴 변 1280px로 축소**해 담는다(원본 미포함).
- 사진 전달은 선택 기능이다. **먼저 `sites.json` 단독 내보내기부터 동작시킨다.**

**⚠ 지점 목록의 원천이 바뀌었다 (2026-08-21 판정, 보고서 §8-1)**

> 사용자: **"조사장소는 정점으로 발주처에서 지정한다. 권역과 트랜섹트 조사여도 정점명으로 관리한다."**

정점을 **발주처(삼성)가 지정**하므로, 지점 마스터의 원천은 조사자료가 아니라 **발주처 지정 문서**다.
위 추출 목록은 등록할 시드가 아니라 **누락·오기 대조용 참고자료**로 지위가 바뀌었다.

- 조류 `평택07` 좌표가 최대 **17.8km** 흩어진 것은 권역 조사라서가 아니라 **데이터 품질 문제**다.
  정점 좌표는 **발주처 목록에서 가져온다.** 조사자료 좌표를 쓰지 않는다.
- 조류·포유류·양서파충류도 어류와 **동일하게 정점 지점으로 등록**한다.
- ⚠ **양서파충류(지점명 0건)는 발주처 목록 없이는 등록이 불가능하다.** 대조할 대상조차 없다.

**→ 선행 조건: 발주처 지정 정점 목록(분류군별 정점명·좌표·설명) 확보.**

**주의해야 할 데이터 이상 (등록 전 사용자 판정 필요)**

- **양서파충류 — 지점 식별 불가.** 820건 모두 `지점명` 칸이 비어 있고, `하천명` 칸에는
  `평택`(383) · `온양`(218) · `용인산단`(103) 같은 **권역명**이나 `1`~`13` 같은 **숫자만** 들어 있다.
  실제 하천명은 `황구지천`(9) · `오산천`(1) 10건뿐이다.
  → 이 상태로는 지점 마스터를 만들 수 없다. **어느 체계를 쓸지 사용자 결정이 먼저다.**
- **`진위천1~5` 가 해마다 다른 장소를 가리킨다** — 2023년과 2025년 좌표가 **17~23km** 떨어져 있다.
  `진위천1~4` 는 하천명도 `진위천`/`송전천`/`용덕사천` 로 갈린다.
  ✅ **판정: 연도별 별개 지점으로 등록**한다(보고서 §8-3). `ValidFrom`·`ValidTo` 로 구간을 나누고
  `SiteName` 자체는 바꾸지 않는다(조사자료의 `Site` 값과 매칭이 깨지면 안 된다).
  ⚠ **잔여 문제**: `진위천1`·`진위천2` 는 **2025분기1차 한 차수 안에 두 곳**(진위천/송전천)이 있어
  연도로도 안 갈린다. 발주처 목록에서 확인해야 한다(§8-4).
- **방류하천과의 관계가 이중으로 어긋난다** (보고서 §7-1)
  - *이름이 같은데 다른 곳* — 생태현황 `오산천1` ↔ 방류하천 `오산천1` (3.6km)
  - *이름이 다른데 같은 곳* — 생태현황 `황구지천1` = 방류하천 `원천리천0` (232m) ·
    `오산천5` = `오산천11` (9m) · `천안온양4` = `곡교천3` (218m)
  - 원인: 방류하천은 **방류구 기준 일련번호**(`원천리천0` 의 설명이 "황구지천 상류"),
    생태현황은 **조사권역 기준 일련번호**. 둘 다 내부적으로는 일관되며 어느 쪽도 틀리지 않았다.
  - ✅ **판정: `Project` 로만 구분한다**(보고서 §8-2). 개명하지 않고 `AliasOf` 도 만들지 않는다.
    대신 조사자 앱에서 **대분류를 바꾸면 선택된 지점을 즉시 해제**하고,
    지점 드롭다운에 **선택된 `Project` 의 지점만** 띄운다. (자료 혼입 방지 — §8-2 체크리스트)
- `황구지천` 과 `황구지천1` 이 별도로 존재한다.
- 하천명 칸에 **숫자 `0`** 이 든 지점: `평택18`·`평택22`·`평택23`. (*빈칸이 아니라 `0` 이다*)
- **포유류 좌표 오류 3건** — 경도 칸에 위도값 2건, 분(分) 자리 오기 1건(서해 해상). (§7-3)
- 분류군 간 지점 체계가 **호환되지 않는다.** 같은 평택 권역을 어류는 `평택1~34`,
  조류는 `평택01~07`, 포유류·양서파충류는 `평택` 하나로 부른다. **입자도 자체가 다르다.**

## 6. [높음] FAI M8 계산 수정 + 과거 데이터 재산출 검토

**결정(2026-08-20): 수생태계 건강성 평가 지침에 따라 M8 비정상종 비율을 실수 나눗셈으로 고친다.**

### 6-1. 코드 수정 (`GB.cs`)
현행은 `abnormalCount`·`totalIndiv`가 모두 `int`라 **정수 나눗셈**이 되어 비율이 사실상 항상 0%다.
→ M8이 언제나 만점(12.5)이 되어 **비정상종 지표가 작동하지 않는다.**

```csharp
// 현행 (결함)
double abnormalRatio = abnormalCount != 0 ? (abnormalCount / totalIndiv) * 100 : 0;
// 수정
double abnormalRatio = totalIndiv > 0 ? (double)abnormalCount / totalIndiv * 100.0 : 0;
```
조사자 앱 `Ecology\EcologyCalculator.cs` 도 **같이** 고쳐야 값이 일치한다.
상세 근거·예시는 `..\..\SDSM_Surveyor\docs\90_TECH_NOTES.md` §5.

### 6-2. 과거 데이터 재산출 (사용자 판단 필요)

기존 `Fish` 테이블의 `FAIScore`·`FAIGrade`·`M8Value`는 **옛 계산(정수 나눗셈)으로 저장**되어 있다.
공식만 고치면 **올해 자료와 과거 자료의 산출 기준이 달라져 연도별 비교가 어긋난다.**

선택지:
- **(가) 과거 데이터 재산출** — 원자료(종별 개체수·DE/EF/LE/TU·하천차수)가 DB에 남아 있으므로 재계산 가능.
  전 연도 일괄 재산출 기능이 필요하다. **실행 전 DB 백업 필수.**
- **(나) 그대로 두고 기록만** — 어느 연도부터 기준이 바뀌었는지 명시. 비교 시 주의가 필요하다.

> ⚠ 사용자(생태 전문가)의 결정 사항이다. 임의로 재산출하지 말 것.
> 재산출을 택하면 변경 전후 값을 대조표로 남겨 어떤 지점의 등급이 바뀌었는지 확인할 수 있게 한다.

### 6-2-1. 먼저 할 일 — **영향 범위 측정 (읽기 전용, DB 수정 없음)**

결정을 눈감고 하지 말고 **숫자를 먼저 본다.** DB를 **읽기만** 하므로 위험이 없다.

1. `SDSMDB.sqlite`를 **읽기 전용으로 열어**(쓰기·백업 불필요) `Fish` 테이블 전체를 훑는다.
2. 각 레코드의 원자료(종별 개체수·DE/EF/LE/TU·하천차수·조사불가사유)로 **새 공식**(M8 실수 나눗셈 + 0종 규칙)을 적용해 재계산한다.
3. **저장값과 비교**해 아래를 집계한다.
   - 전체 레코드 수 / 값이 바뀌는 레코드 수
   - **등급이 바뀌는 레코드 수**(A→B 처럼) — 이것이 핵심 지표다
   - 등급 변화 분포(예: C→D 12건, D→E 3건)
   - 연도별·지점별 분포 (특정 연도에 몰리는지)
   - 0종이라 `37.5·D`로 저장돼 있던 레코드 수
4. 결과를 `..\..\SDSM_Surveyor\docs\_recalc_impact_YYYYMMDD.md` 로 남긴다.

> ⚠ **DB에 쓰지 않는다.** 이 단계는 순수 분석이다. 재산출 실행은 사용자 결정 후 별도로 한다.

### 7-1. 평가항목 전부 미입력 시 — **`null`(`-`)로 통일** (2026-08-20 결정)

대조 재실행에서 남은 4건. 같은 자료인데 경로에 따라 다르다.

| 경로 | 현행 |
|---|---|
| 편집화면 | **점수 `0` · 등급 `E`** |
| 일괄입력(DB 저장) · 조사자 | `null` (`-`) |

**결정: 일괄입력·조사자 쪽(`null`)이 맞다. 편집화면을 그쪽으로 통일한다.**

근거 — 이 앱의 **결측(null)과 0을 엄격히 구분**하는 원칙(`CLAUDE.md` §7.2)이 그대로 적용된다.
- **항목이 비어 있음** = 아직 평가하지 않음 → `-` (평가 불가)
- **모든 항목을 0점으로 선택** = 실제 평가 결과 → 점수 `0` · 등급 `E`

HRI는 종을 세는 것이 아니라 **항목마다 점수를 고르는** 평가다. 고르지 않은 것을 "0점을 매겼다"로 취급하면,
평가를 안 한 지점이 **최하등급으로 DB에 남는다.** 어류 0종을 `E`로 정한 것과 모순되지 않는다 —
그쪽은 조사자가 **`출현종 없음(0종)`을 명시적으로 선언**한 경우이고, 이쪽은 선언 없이 비어 있는 경우다.

> 조사자 앱은 `HriOption?`으로 미선택(null)과 0점 선택을 이미 구분하므로 수정할 것이 없다.

#### ✅ 완료 (2026-08-20)

`HabitatWaterEdgeEditorControlViewModel.GetGrade()` 반환형을 `(double, string)` → **`(double?, string?)`** 으로 바꾸고,
평가항목 합이 0이면 점수·등급을 `null`로 둔다. 조사불가일 때 `-`를 넣는 분기도 명시했다(초기값이 null이 되었으므로).
호출부 2곳(`AddItemToModel`·`IsEditItemToModel`)은 `EvaluationScore`(`double?`)·`EvaluationGrade`(`string?`)에
그대로 대입하므로 수정할 것이 없었다.

**결과: 계산식 대조 1,388건이 전부 일치한다(불일치 0).** 편집화면·일괄입력·조사자 세 경로의 HRI 값이 동일해졌다.

> ⚠ **남은 한계**: 세 경로 모두 `합계 != 0` 으로 판정하므로, **10개 항목을 전부 0점으로 선택**해도
> 미입력과 똑같이 `null`(`-`)이 된다. 실제로 완전히 훼손된 하천(전 항목 0점)이 있을 수 있으므로,
> 이를 `0·E`로 구분하려면 **세 경로 모두** "값이 하나라도 입력되었는지"로 판정을 바꿔야 한다.
> 이번 결정(§7-1)은 미입력 처리만 다뤘으므로 그대로 두었다. 필요하면 별도 과제로 진행한다.
