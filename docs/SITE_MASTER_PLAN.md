## 2. 뿌리 문제 — 지점 식별자 (다른 모든 것보다 먼저 정한다)

**현재 구조**

- `SurveySite.SiteName` 주석: *"DB상 지점명. 조사자료의 `Site` 값이며 **이 앱의 지점 식별자**다"*
- `CLAUDE.md` §8-1: *"조사자료의 `Site` 값과 매칭이 깨지므로 **지점명 자체를 바꾸지 않는다**"*
- `SiteResolver.Resolve()` 는 **문자열 비교**로 지점을 찾는다(공백 제거·대문자)

**그런데 이번 요구는 지점명 수정·병합·일괄변경을 정면으로 요구한다.**
현행 `SaveSiteExecuted`·`MergeSiteExecuted`·`DeleteSiteExecuted` 는 **`sites.json` 만 고치고 DB 조사자료는 건드리지 않는다.**
지금 상태로 이름을 바꾸면 그 지점의 과거 조사자료는 **조용히 고아가 된다.** 오류도 경고도 나지 않는다.

### 선택지

| | (가) `SiteId` 도입 **[권고]** | (나) 이름 유지 + 변경 시 DB 동시 치환 | (다) 이름 수정 금지(현행) |
|---|---|---|---|
| 방식 | 불변 식별자(예: `ECO-0042`) 신설. `SiteName` 은 표시용 | 이름을 바꾸면 같은 트랜잭션에서 조사자료 `Site` 를 일괄 UPDATE | 이름은 못 고치고 별칭만 추가 |
| 조사자료 | `Site`(문자열) 유지 + `SiteId` 열 추가, 과거분 1회 매핑 | 스키마 변경 없음 | 변경 없음 |
| 이름 변경 | 안전 — 자료는 ID로 붙어 있다 | 위험 — 치환 실패 시 절반만 바뀐다 | 불가 |
| 병합·분할 | 안전 | 조사자료 대량 UPDATE 필요 | 불가 |
| 조사자 앱 | 오프라인 세션에도 SiteId 저장 | 이름만 알면 됨 | 현행 |
| 작업량 | 중(모델 7테이블 + 매핑 스크립트 + 하네스) | 소~중 | 없음 |
| 되돌리기 | 쉬움 | 어려움 | — |

> ✅ **확정: (가) `SiteId` 도입** (2026-09-07). R-2·R-3·R-4 를 전부 열면서 (나)로 버티면, 일괄변경 한 번이 과거 자료 수백 건을 끊을 수 있다.
> (가)를 채택하면 §3~§5 의 나머지 기능은 전부 안전한 편집이 된다.
> ⚠ 다만 (가)는 **조사자료 7개 테이블 스키마 변경**이므로 `CLAUDE.md` §0 의 "파괴적 변경 사전 고지" 대상이다.

## 3. 기능 A — 생태현황 기초틀 일괄 등록 (R-1)

### 3-1. 등록 규칙

- **지점 단위 = (하천명, 지점명) 조합.** 지점명이 같아도 하천명이 다르면 별개 지점으로 등록한다.
- **빈칸은 채우지 않는다.** 좌표·하천차수·설명·St번호·사업장이 없으면 `null` 로 두고, 화면에 **"보완 필요"** 로 표시한다.
- 상태는 `Draft`(기초틀). 발주처 확정 전임을 화면과 배포본에서 구분한다.
- `Taxa`(적용 분류군)는 **그 지점이 실제로 나온 분류군만** 체크한다(어류에서 나온 지점은 `["어류"]`).

### 3-2. 예상 등록 규모 (게시버전 DB 기준)

| 분류군 | 조사기록 | 고유 지점명 | **(지점,하천) 조합 = 등록 건수** | 지점명 빈칸 |
|---|---:|---:|---:|---:|
| 어류 | 127 | 118 | **122** | 0 |
| 조류 | 3,077 | 28 | **29** | 931 (30%) |
| 포유류 | 445 | 3 | **6** | 175 (39%) |
| 양서파충류 | 820 | 0 | **0** | 820 (100%) |
| 합계 | | 149 | **157** | |

- 복합키를 쓰면 149 → **157건**이 된다(같은 지점명이 하천명 2종을 갖는 8건이 갈라진다).
- 양서파충류는 지점명이 0건이라 §10 판정 ①(자동 채번)을 적용한다 → **18건 추가**, 총 **175건**.
  다만 그 18건의 성격에 문제가 있다 → **§3-4**.

### 3-4. ⚠ 양서파충류 자동 채번 — 원자료 확인 결과 (2026-09-07)

원본 `2603_생태현황_양서파충류_DB_v1.xlsx` 의 `양서파충류` 시트를 열어 확인했다.

- 양식은 **E열 = 하천명(대상지명), F열 = 지점명(`하천명_숫자` 형식)** 으로 되어 있다.
- **F열(지점명)은 820행 전부 비어 있다.** 조사자가 채우지 않았다.
- 더 큰 문제는 E열이다. **연도에 따라 다른 것이 들어가 있다.**

| 연도 | E열에 들어간 값 | 건수 | 실제 의미 |
|---|---|---:|---|
| 2023~2024 | `평택` 383 · `온양` 218 · `용인산단` 103 · `황구지천` 9 · `오산천` 1 | 714 | **하천이 아니라 조사권역**(황구지천·오산천만 실제 하천) |
| 2025 | `1`~`13` (숫자) | 106 | **하천명 칸에 지점번호를 적었다** |

**따라서 `하천명-01` 을 기계적으로 적용하면 이렇게 된다.**

| 생성될 지점명 | 묶이는 기록 | 문제 |
|---|---:|---|
| `평택-01` | 383 | 권역 전체가 지점 1개. 사실상 지점 구실을 못한다 |
| `온양-01` | 218 | 동일 |
| `용인산단-01` | 103 | 동일 |
| `황구지천-01` · `오산천-01` | 10 | 정상 |
| `1-01` ~ `13-01` | 106 | **지점명이 숫자다.** 하천을 알 수 없다 |

**좌표로 쪼개는 방법도 쓸 수 없다.** 820건 전부 좌표가 있지만 300m 격자로 나누면 **319개 군집**이 나온다.
양서파충류는 정점 조사가 아니라 답사(踏査)형이라 관찰 좌표가 흩어진다. 지점 319개는 실제 조사 체계와 무관하다.
(좌표 자체에도 오류가 있다 — 경도 최대값이 **137.18°**로 한반도 밖이다. 도·분 분리 입력의 변환 오류로 보인다)

**그래서 판정 ① 은 이렇게 좁혀 적용한다.**

| 원자료 E열 | 등록 지점명 | 상태 | 보완 필요 표시 |
|---|---|---|---|
| 권역명(평택·온양·용인산단) | `평택-01` 등 3건 | `Draft` | **정점 세분 필요** |
| 실제 하천명(황구지천·오산천) | `황구지천-01` · `오산천-01` 2건 | `Draft` | 좌표 |
| 숫자(1~13) | `양서_St1` ~ `양서_St13` 13건 | `Draft` | **하천명 미상** |

- 합계 **18건**. 전부 "고쳐야 하는 기초틀"이라는 표식을 달고 들어간다.
- 이 18건은 **조사자 드롭다운에서 기본으로 숨기고**, [보완 필요 지점도 보기] 를 켜야 나오게 한다.
  그대로 노출하면 2026년 조사자가 `평택-01` 을 골라 또 권역 단위로 입력한다 → 같은 문제가 한 해 더 쌓인다.
- **근본 해결은 발주처 정점 지정이다.** 위 18건은 그때까지의 임시 골격일 뿐이다.

### 3-3. 화면

`[설정] → [조사지점 관리]` 에 **[일괄 등록]** 탭 신설

1. 원천 선택 — ⓐ 현재 DB의 조사자료에서 추출 ⓑ 엑셀 파일 ⓒ 붙여넣기
2. 미리보기 그리드 — 신규/기존중복/충돌 3색 구분, 등록 제외 체크
3. 대분류·기본 사업장 지정(공통값)
4. [등록] — 마스터에 `Draft` 로 추가, **파일 저장은 별도 [마스터 저장]** (현행 규칙 유지)

## 4. 기능 B — 관리자 일괄 수정 (R-2·R-3)

### B-1. 그리드 다중선택 일괄 변경

- 트리 옆에 **평면 그리드 뷰**를 추가한다(현재는 트리만 있어 다중선택이 안 된다).
- 필터: 대분류(**강제**)·사업장·과업대표하천·상태·"빈 항목만" 토글
- [선택 항목 일괄 변경] → 대상 필드 1개 선택 → 새 값 입력 → **변경 전후 미리보기** → 적용
- 일괄 변경 허용 필드: `Workplace` · `River` · `SiteGroup` · `Chasu` · `Taxa` · `ValidFrom/To` · `Project`
- **`SiteName` 은 일괄 변경에서 제외한다**(단건 편집에서만, §2 결정 이후)

### B-2. 엑셀 왕복

- [지점 목록 내보내기] → xlsx (헤더 = 모델 필드, `SiteId` 열 포함·잠금)
- 사용자가 엑셀에서 편집 → [지점 목록 가져오기]
- **diff 화면**: 변경 N건 · 신규 M건 · 삭제 K건, 행별 전후 대조 → 선택 적용
- 검증: 필수값·좌표 범위(위도 33~39, 경도 124~132)·대분류 값·중복(대분류+이름+연도구간)

### B-3. 안전장치 (없으면 만들지 않는 편이 낫다)

- **적용 전 미리보기 필수** — 미리보기 없는 일괄 적용 버튼을 만들지 않는다
- **되돌리기** — 적용 직전 `sites.json` 스냅샷을 `SiteBackups\sites_yyyyMMdd_HHmmss.json` 로 남기고 1클릭 복원
- **변경 이력** — 누가·언제·무엇을(필드·전후값·건수) `site_audit.log` 에 CSV 로 남긴다
- **낙관적 잠금** — `SiteCatalog.Version` 을 읽은 시점과 저장 시점이 다르면 경고

## 5. 기능 C — 조사자 지점 추가 → 관리자 확정 (R-4)

### 5-1. 상태 전이

```
             조사자 추가            관리자 승인
   (없음) ──────────────▶ Proposed ──────────▶ Confirmed
                             │  │                  ▲
                    반려     │  │  병합            │  발주처 확정
                             ▼  └──────────▶ (기존 지점에 흡수)
                          Rejected
   조사자료 추출 ────▶ Draft ──────────────────────┘
                        (기초틀 · 보완 필요)
```

| 상태 | 뜻 | 조사자 앱 표시 | 배포본 포함 |
|---|---|---|---|
| `Confirmed` | 발주처·관리자 확정 | 일반 항목 | ○ |
| `Draft` | 조사자료에서 만든 기초틀 | 일반 항목 + "보완 필요" 표식 | ○ |
| `Proposed` | 조사자가 추가, 검토 대기 | "내가 추가함 · 검토 중" | △ 제안자 로컬만 |
| `Rejected` | 반려 | 사유와 함께 회색 표시, 선택 불가 | × |
| `Retired` | 더 안 쓰는 지점 | 과거 연도에서만 보임 | ○ |

### 5-2. 조사자 앱 (SDSM_Surveyor)

1. 지점 드롭다운 맨 아래 **[+ 이 목록에 없는 지점 추가]**
2. 입력: 하천명(필수) · 지점명(필수) · 좌표(선택, 현재 위치/지도) · 설명 · 대분류(현재 선택값 고정, 변경 불가)
3. **중복 방지** — 저장 직전 ⓐ 좌표 반경 300m 내 기존 지점 ⓑ 이름 유사(공백·번호 제거 후 일치) 를 제시하고 *"이 지점 아닌가요?"* 확인
4. 저장 위치는 **`%AppData%\SDSM_Surveyor\sites_user.json` overlay** — 번들 `sites.json` 은 건드리지 않는다(종목록 overlay `C-7b` 와 같은 패턴). 마스터가 교체돼도 제안분이 보존된다
5. 조사·내보내기는 즉시 가능. 엑셀 지점 열에 **`[제안]`** 접두 표기
6. 동기화 시 관리자 판정 결과를 받아 상태를 갱신하고, 승인·병합으로 이름이 바뀌면 **로컬 세션의 지점 값도 함께 갱신**한다

### 5-3. 관리자 앱 (SDSM_App)

- [조사지점 관리] → **[검토 대기]** 탭. 목록: 제안자·제안일·대분류·하천·지점명·좌표·해당 조사자료 건수
- 각 건에 **유사 지점 후보**를 자동 제시(좌표 거리순 + 이름 유사도)
- 판정 3택: **승인**(그대로 등록) · **병합**(기존 지점에 흡수, 이름 치환 대상 표시) · **반려**(사유 필수)
- 판정 결과를 `sites.json` 에 반영 → [조사자 배포본 내보내기] → 교환소 폴더

### 5-4. 편집 권한과 마스터 보유 (판정 ④ = **둘 다** 에 따른 운영 규칙)

용역사와 삼성 담당자가 **둘 다** 편집·승인할 수 있다. 그런데 `sites.json` 은 **파일 통째 교환**이라
양쪽이 각자 고치면 나중에 보낸 쪽이 상대의 편집을 **통째로 지운다**(맹점 16). 그래서 규칙을 둔다.

| 항목 | 규칙 |
|---|---|
| 마스터 보유 | **한 곳만 원본을 갖는다.** 기본은 관리자 앱이 설치된 삼성 담당자 PC |
| 상대편 편집 | 자기 사본을 고친 뒤 **[변경 제안 내보내기]** 로 변경분만 파일로 만들어 전달 |
| 병합 | 마스터 보유자가 [변경 제안 가져오기] → **diff 확인 → 선택 적용** (§4 B-2 와 같은 화면 재사용) |
| 이력 | 모든 편집에 **누가**(Windows 계정 + 앱 로그인 계정)를 남긴다. `site_audit.log` |
| 확정 승격 | `Draft`/`Proposed` → `Confirmed` 승격은 **양쪽 다 가능**하되, 승격 이력에 승격자를 남긴다 |
| 충돌 | `SiteCatalog.Version` 이 다르면 저장을 막고 "먼저 최신본을 가져오세요" 안내 |

> ⚠ 마스터를 **양쪽이 동시에 보유하는 구성은 만들지 않는다.** 실시간 동기화 서버가 없으므로
> (`C-10` 결정 — 서버 동기화 보류) 두 원본은 반드시 어긋난다.

## 6. 데이터 모델 변경안 (합의 후 구현)

```csharp
public class SurveySite
{
    // 신규 — §2 에서 (가) 채택 시
    public string SiteId { get; set; }          // 불변 식별자. 예 "ECO-0042" · "REL-0007"

    // 신규 — 상태·출처·보완
    public SiteStatus Status { get; set; }      // Confirmed / Draft / Proposed / Rejected / Retired
    public string? Origin { get; set; }         // "조사자료추출" · "조사자제안" · "발주처확정" · "관리자입력"
    public string? ProposedBy { get; set; }     // 제안 조사자
    public DateTime? ProposedAt { get; set; }
    public string? ReviewNote { get; set; }     // 반려 사유 · 병합 대상
    public List<string> NeedsFix { get; set; }  // 보완 필요 항목 ["좌표","하천차수"]
    // 기존 필드는 그대로 둔다
}
```

- 조사자료 7개 테이블에 `SiteId`(nullable) 추가 — 과거분은 이름 매핑 스크립트로 1회 채운다
- **하위 호환**: `SiteId` 가 없는 `sites.json`(sites-20260821)도 오류 없이 로드되어야 한다. 로드 시 자동 채번

### 6-1. `SiteId` 표기 규칙 (확정)

- 형식 `REL-0001` (방류하천) · `ECO-0001` (생태현황). 4자리 일련번호, 대분류별로 독립 채번
- **생성 시점에 한 번 부여하고 이후 절대 바꾸지 않는다.** 대분류를 나중에 정정해도 **ID 접두어는 그대로 둔다**
  (접두어는 사람이 알아보기 위한 관례일 뿐이며, 어떤 로직도 접두어에서 대분류를 읽지 않는다)
- 삭제한 지점의 번호는 **재사용하지 않는다** (과거 자료가 그 ID 를 참조하고 있을 수 있다)
- 조사자 제안 지점은 `PRO-` 접두어로 임시 발급하고, 승인 시 `ECO-`/`REL-` 로 **재발급하지 않는다** — 그대로 둔다
  (재발급하면 제안 기간에 쌓인 자료가 끊긴다 — 맹점 2)

### 판정 이후 새로 확인된 것 — 착수 전 한 번 더 볼 것

1. **양서파충류 자동 채번의 실질**(§3-4) — 18건 중 3건은 권역 1지점(383·218·103기록), 13건은 지점명이 숫자다.
   기계적으로는 판정 ①대로 만들 수 있으나, **이 지점들로 2026년 조사를 하면 같은 문제가 한 해 더 쌓인다.**
   → 조사자 드롭다운 **기본 숨김**으로 막되, 발주처 정점 지정을 별도로 요청하는 편이 안전하다.
2. **양서파충류 좌표 오류**(맹점 17) — 경도 최대 137.18°. 등록·중복검사 전 범위 필터 필요.
3. **권한 "둘 다"의 대가**(§5-4) — 마스터 원본을 양쪽이 각자 보유하면 반드시 어긋난다. 보유자 1곳을 지정해야 한다.

### 착수 승인 상태

- S0~S7 착수 가능. 다만 **S0(`SiteId`)는 스키마 변경**이므로 실제 코딩 착수 전에 한 번 더 고지한다.
- 발표 시연에는 S2(기초틀 등록)까지만 있으면 된다.
